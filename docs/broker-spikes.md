# Broker research spikes — empirical findings

Two research spikes run 2026-08-09 for the Agent Capability Broker workstream
(issues #77 and #74). Both were run **on the real target host** (Linux arm64
single-board machine, Go 1.26) with working prototypes, not desk research — the
conclusions below changed the `brokerd` design and are cited from
`backend/internal/broker/socket.go` and `backend/internal/broker/keyring/` —
both introduced by the brokerd PR (#102), not by this document.

Preserved here because the applied conclusions live in code comments but the
evidence behind them did not, and the next person to ask "why not just check
`/proc/<pid>`?" or "why memguard rather than a plain `[]byte`?" deserves the
reproduction, not a restatement of the verdict.

## Spike #77 — Socket authorization: who is the calling principal?


### Empirical findings (all reproduced live on this host, then cleaned up)

1. **SO_PEERCRED basics.** `unix.GetsockoptUcred(fd, SOL_SOCKET, SO_PEERCRED)` on the accepted `*net.UnixConn`'s raw fd returns the true, kernel-supplied `{pid, uid, gid}` of whatever process called `connect()`. Verified correct for a Go binary and for a Python-invoked client. The client cannot lie about this via any socket API — it's not client-supplied data.

2. **SO_PEERCRED is latched at connect() time, not live.** Re-reading `SO_PEERCRED` on the same fd later in the connection returns byte-identical values (confirmed `ucred2 == ucred`) regardless of what happens to the peer process afterward. This is the well-documented `unix(7)` semantics: "credentials... in effect at the time of the call to connect()."

3. **uid/gid buy nothing here.** Both the legitimate client and every "attacker" process in these tests report `uid=1000, gid=1000` — exactly the framing in the task ("everything runs as the operator's own OS user, so UID alone distinguishes nothing"), now confirmed rather than assumed.

4. **Socket path + directory permissions gate cross-user access, and only that.** With the socket at `0600` inside a `0700` operator-owned directory, connecting as `nobody` (via `sudo -n -u nobody`) failed at `connect()` itself with "permission denied" — it never reached `accept()`/`SO_PEERCRED` at all. Same-uid processes connect freely regardless of which one they are. So: necessary hygiene against a *different* OS user or a misconfigured world-writable socket, structurally incapable of discriminating within one uid — exactly the population chuvar's threat model cares about.

5. **PID exact-reuse TOCTOU is real but currently hard for this specific adversary, and that's a fragile, non-portable fact.** `/proc/sys/kernel/ns_last_pid` (the file that lets you deterministically win a PID-reuse race, a documented technique) shows DAC permission bits `rw-rw-rw-`, but writing to it as an unprivileged user failed with an OS-level permission error — the kernel enforces `CAP_SYS_ADMIN` over the DAC bits for this specific sysctl. A probabilistic spray of 4000 concurrent `/bin/true` executions immediately after a target process exited did not land on its exact freed PID (unsurprising: `pid_max=4194304`, allocation is monotonic, exact-number reuse without the privileged shortcut requires wraparound-scale process volume). **Conclusion: don't treat this as "PID reuse isn't a risk" — treat it as "this specific host/kernel config happens to block the cheap, deterministic version of the race for an unprivileged same-uid attacker." It is not something brokerd's design should depend on holding elsewhere (containers, different capability grants, different kernels).**

6. **The TOCTOU that matters much more, and requires no race at all: `/proc/<pid>/exe` (and `cmdline`) are live, not latched.** Built a "shapeshifter" client that connects (so `SO_PEERCRED` correctly captures its real pid/uid at that instant, while it is still running the legitimate-looking binary), then `execve()`s into a completely different binary while holding the *same pid* and the *same already-open connection* (had to explicitly clear `FD_CLOEXEC`, since Go sets it by default on sockets). Result, reproduced cleanly:
   - `SO_PEERCRED` at accept time: `pid=2236710`, correctly identifying the connecting process.
   - The server's *delayed* secondary check (deliberately simulating "broker does some work — parse payload, hit the DB — between accept and using the pid"), 600ms later: `/proc/2236710/exe` now resolves to `bin_postexec`, a different binary the process only became after the connection was already accepted, while `SO_PEERCRED` (re-read at the same moment) still reports the same frozen `pid/uid/gid`.
   - **This means any `/proc/<pid>`-based secondary identity check performed any time after the single synchronous `SO_PEERCRED` read is checking attacker-influenceable, mutable state — not something the kernel froze for you.** No PID-number race is needed; the process just needs to do something (legitimately or under injection) between connecting and being checked.

7. **`exe`-path pinning is separately weak for interpreted callers.** A Python client's `/proc/<pid>/exe` resolves to `/usr/bin/python3.13` — the interpreter, not the script. Any same-uid attacker can also just run `python3` and present an identical `exe` path. So exe-allowlisting authenticates "this OS user ran the interpreter/binary at this path," not "this specific trusted script/session" — a real gap if brokerd's legitimate caller (the shim) is ever interpreted rather than a dedicated static binary.

8. **`cmdline` (argv) is always fully attacker-controlled and always readable**, regardless of the process's dumpable state (confirmed: readable even when `PR_SET_DUMPABLE=0` blocks `exe`/`environ`/`mem`). Never usable as a trust signal, full stop.

9. **`environ` is readable same-uid by default (confirmed: 6.4KB read successfully across all same-uid tests) but is also fully attacker-set at exec time** — even where reading it is blocked, its *contents* were never a trust signal, only its *readability* is a hygiene concern (secret leakage risk, not identity proof).

10. **`PR_SET_DUMPABLE(0)` is an effective, verifiable mitigation for the leakage side.** After a process calls `prctl(PR_SET_DUMPABLE, 0)`, same-uid attempts to `readlink /proc/<pid>/exe`, read `/proc/<pid>/environ`, or `readlink /proc/<pid>/cwd` all fail with "Permission denied" (confirmed live). This is the concrete mechanism that makes an env/fd-based secret handoff to a small trusted shim process resistant to scraping by *other* same-uid processes (including a confused/injected sibling the agent's own shell spawns) — while `cmdline` remains readable regardless (finding 8), so secrets must never go there.

11. **cgroup path is a real, kernel-enforced, per-session signal on this host's harness** (`tmux-spawn-<uuid>.scope`, identical across nested sub-shells of one session) but this is a property of *this* launcher/harness, not something brokerd's design can assume every agent-host deployment provides — usable as a supplementary, logged signal where available, never load-bearing on its own.

### Direct answers to the three questions

- **Who is the calling principal?** Not the OS user (singular, useless here) and not a bare PID (weak — frozen-but-content-free at connect time, and anything read from `/proc/<pid>` afterward is live and attacker-influenceable, findings 5–9). The only sound answer is **a grant-bound session**, identified by possession of a per-session secret minted at grant time (human present) and held only by a launcher-controlled shim process — never by the agent's own general-purpose tool-execution context.
- **How do we know?** Two kernel-enforced, unspoofable facts checked **synchronously, at accept time, with zero intervening I/O**: (a) `SO_PEERCRED.Uid` equals the operator's own uid (cheap, catches a genuinely different OS user/service account even though it's a near-no-op on this single-user host), and (b) the connecting party presents the pre-shared per-grant token on that same connection, matched against an active row in the existing `grants`/`grant_scopes` consent-plane tables.
- **What happens if they lie?** No token, wrong token, uid mismatch, or a token that doesn't cover the requested scope → reject with the doc's existing typed failure codes (`NO_GRANT`/`SCOPE_DENIED`), write an append-only `audit_log` row recording the attempt (including the observed-but-untrusted uid/pid, kept for forensics only, never for authorization), and feed repeated failures into the doc's existing `RATE_LIMITED` anomaly tripwire — fail closed, loudly, per CLAUDE.md principle 5, not a log line.

### Recommendation

Treat socket authorization as two independent, composable controls, because the empirical results show no single check covers chuvar's stated adversary (a confused/injected agent process **and** any other same-user process): (1) a cheap, kernel-enforced **uid gate** via `SO_PEERCRED`, read synchronously at `accept()` before touching the payload or the DB — reject anything whose `Uid` isn't the operator's own, purely as free defense-in-depth against a genuinely different OS/service account; and (2) the actual authorization primitive, a **per-grant, per-session pre-shared token**, minted only at grant time (human present, via the existing approval control plane — no new surface) and stored hashed alongside the `grants` row (`kind='capability'`) the doc already has. Never use `/proc/<pid>` state (`exe`, `cmdline`, `cgroup`, `environ`) as an authorization input — findings 6–9 show it's either fully attacker-controlled or live-mutable after the one moment `SO_PEERCRED` is trustworthy; log `pid`/`exe` for audit/forensics only, and only ever act on it as a *supplementary, logged* signal (e.g. a launcher-provided cgroup match, finding 11) where a specific deployment's harness happens to provide it — never load-bearing.

The token's handoff is the design's actual hard problem, and it must go **out of band from the agent's own tool-execution context**, not merely "out of band from the socket": mint it at grant time into a small, launcher-spawned, dedicated shim process (the thing `gpg.ssh.program` invokes) that is a *sibling*, not a *child*, of the agent's general-purpose shell tool — if the token ever transits an env var or file the agent's own bash tool can also read, it becomes ambient per CLAUDE.md principle 3 regardless of how it arrived, and a prompt-injected agent can just `cat`/`env` it out. Immediately on receiving the token, the shim should call `prctl(PR_SET_DUMPABLE, 0)` — confirmed live in this spike to block same-uid `/proc/<pid>/exe|environ|mem` reads from any sibling process, closing the in-band-leakage path at the kernel level rather than relying purely on process-tree hygiene. The token is then presented on *every* socket connection (not cached broker-side as "already authenticated once"), checked in the same synchronous accept-time code path as the uid check, with the token consumed on the same read that authorizes the same signing request it accompanies — eliminating any deliberate delay between "check" and "use." Be explicit in the design doc about the residual, out-of-scope case matching §3.0's existing framing: `ptrace`-scraping the shim's memory after `PR_SET_DUMPABLE(0)` to steal the live plaintext token, or ns_last_pid-style deterministic PID racing, both require privilege (`CAP_SYS_PTRACE`/`CAP_SYS_ADMIN`) this spike confirmed an unprivileged same-uid attacker does not have on this host — attack-shaped, tripwire-able, not prevented, exactly like the existing DB-container-exec carve-out, not a gap this control claims to close. Finally, keep the existing "broker never blind-signs" payload check as the second, independent control: the socket layer answers *who may ask*; the SSHSIG-namespace/committer-identity check answers *what they may get signed regardless of who's asking* — both are needed, and neither substitutes for the other.

## Spike #74 — In-memory key custody in Go

All work done in `/tmp/keycustody-spike` (a disposable Go module, now deleted — the repo working tree was not modified). Read in full before starting: `AGENTS.md` (esp. §3.0 trust boundary, §3.5 sealed-at-rest, §6 review discipline), `backend/internal/custody/{custody,backend,custody_test}.go`, and `docs/capability-broker.md` (Custody model section + the 2026-08-01 and 2026-08-09 decision-log entries, esp. "brokerd holds decrypted key material ... in process memory for the grant duration").

### Host facts (verified, not assumed)
- `uname -a`: Linux aarch64 (Raspberry Pi 5), kernel 6.18.34+rpt-rpi-2712.
- Go 1.26.5 linux/arm64 (via the repo's `mise.toml`; `mise exec --` only resolves `go` inside the chuvar tree, so the spike pinned the resolved absolute binary path for use from `/tmp`).
- **Page size is 16384 bytes** on this host (`getconf PAGESIZE`) — not the common 4096 on x86_64. This directly explains several measurements below.
- `RLIMIT_MEMLOCK` soft **and** hard = 8388608 bytes (8MB), confirmed via `ulimit -Sl/-Hl`, Python `resource.getrlimit`, and `prlimit`. Attempting to raise it via `systemd-run --user -p LimitMEMLOCK=infinity` still reported 8MB — but this session's own `CapEff` is empty (`0000000000000000`) despite a full bounding set, so I could not cleanly separate "this host truly caps at 8MB regardless of privilege" from "this sandboxed agent session specifically can't raise it." **Flagging as unresolved, not settled** — needs re-checking from a real, unsandboxed systemd unit before treating 8MB as an absolute ceiling for a production `brokerd` deployment.
- No Yama LSM (`/proc/sys/kernel/yama` doesn't exist) — classic ptrace model in force (any same-uid process may `ptrace` another *unless* the target is non-dumpable). `PR_SET_DUMPABLE=0` is therefore load-bearing on this host, not redundant with a stricter Yama policy.
- Swap enabled (2GB, ~1.8GB in use at test time) — makes `mlock` a real, non-decorative concern here, not a theoretical one.

### memguard v0.23.0 on this arm64 host — verified, not assumed
Built and ran real `/tmp` prototypes (not reasoning from the README):
- Core round trip works: `NewEnclave` → `Enclave.Open` → `LockedBuffer.Bytes/Wipe/Destroy` all function correctly on arm64.
- `mlock` genuinely takes effect (not silently degrading) — confirmed via `/proc/self/status` `VmLck` deltas before/after allocation.
- **`Destroy()` truly unmaps memory, it doesn't just zero it.** Discovered this the hard way: an earlier draft of my test kept a `[]byte` alias across `Destroy()` and touching it afterward produced `fatal error: fault` / `SIGSEGV` — an **unrecoverable** process crash (not a catchable Go panic), confirmed via a subprocess harness (`syscall.WaitStatus`, `SIGSEGV`). A lingering alias into a destroyed `LockedBuffer` anywhere in a codebase kills the whole process, not just that call site.
- **API footgun found:** calling `Wipe()` on a buffer produced by `NewBufferFromBytes` (which internally calls `Freeze()`, i.e. `mprotect(PROT_READ)`) SIGSEGVs immediately (`SEGV_ACCERR`, a write against a read-only mapping) instead of returning an error. `Wipe()` trusts the caller to have `Melt()`ed a frozen buffer first and has no graceful failure path if they haven't. Any brokerd wrapper must use `NewBuffer(n)+Copy(raw)` (mutable) for anything it intends to `Wipe()` mid-lifetime, and reserve `NewBufferFromBytes`/immutable buffers for hold-until-Destroy usage.
- **`PR_SET_DUMPABLE` is NOT set by memguard.** Grepped the entire vendored source of `memguard` and its `memcall` dependency (`v0.4.0`) for `DUMPABLE`/`PR_SET`: zero occurrences. Confirmed live via `prctl(PR_GET_DUMPABLE)` after normal library use: still `1` (dumpable). What `memcall_unix.go` *does* apply per-buffer is `mlock` + `MADV_DONTDUMP` — the latter only excludes those specific pages from a *core dump*; it does **not** block a same-user process from `ptrace`-attaching or reading `/proc/<pid>/mem` live. **brokerd must call `PR_SET_DUMPABLE=0` itself, once, at boot** — no library in this evaluation does it.
- **mlock/RLIMIT_MEMLOCK budget, measured exactly:** each 32-byte memguard key costs exactly **one page (16KB on this host)** of locked memory — not 3-4 pages as the guard-page architecture might suggest, because the `PROT_NONE` guard pages are never `mlock`ed (nothing to protect there). Under this host's 8MB `RLIMIT_MEMLOCK`, that's a hard ceiling of **~512 concurrent 32-byte keys**, measured directly (512 successful allocations, then failure).
- **Exceeding the ceiling panics, and the panic wipes every other currently-held key, not just the failing one.** `core.Panic` = `Purge()` (destroys the *entire* buffer registry) then a normal Go `panic(v)`. Confirmed experimentally: recovered the panic with `defer recover()` (it IS a normal recoverable Go panic, not a fatal runtime error), then checked all 512 previously-good buffers — every single one now reports `IsAlive() == false`. **This is a real cross-grant blast-radius bug waiting to happen**: one over-budget allocation (e.g. a burst of concurrent grant requests) silently destroys every other active grant's key material unless the caller (a) wraps every custody allocation in `recover()`, and (b) enforces its own concurrent-grant ceiling well below the mlock-derived one, and (c) treats hitting that ceiling as an audited tripwire event, not an ungraceful crash a process supervisor just restarts past.

### Hand-rolled mmap+mlock+guard-pages — built and verified
Implemented from scratch (~140 lines, `golang.org/x/sys/unix` only, already an indirect dependency of `backend/go.mod`): anonymous `mmap`, `mlock` only the data page, `MADV_DONTDUMP` the 3-page region, `mprotect(PROT_NONE)` guard pages before/after, explicit zero+`munlock`+`munmap` on `Destroy`.
- Round-trip works; `Destroy()` deliberately unmaps (not just zeroes) for the same "crash loud, not silent" reasoning as memguard.
- **Guard pages genuinely fault** — verified via a standalone binary (not `go test`, see below) touching one byte before and one byte after the data page: both SIGSEGV as expected, on both sides.
- Same mlock economics as memguard: exactly one page (16KB) locked per key here, because only the data page is locked, not the guards — **hand-rolling buys no mlock-budget efficiency win over memguard on this host**; the per-key cost is an OS page-granularity constraint, not a library implementation detail.
- **Missing vs. memguard**: no encrypted-at-rest "enclave" concept (memguard's `Enclave` keeps buffers not currently in use AES-encrypted with a canary, further shrinking the live-plaintext window — directly relevant to "hold for the grant duration"), no canary-based corruption detection, no `CatchInterrupt`/signal-triggered wipe-all, no cross-platform abstraction (this prototype is Linux/Unix-syscall-specific; memguard handles Windows/macOS/BSD variants too, though chuvar's near-term deployment is Linux-only).
- **Methodology trap worth naming**: my first attempt to verify the guard-page fault via `go test -run ... ` recursion produced a silent, incorrect "PASS" — the child `go test` process exited cleanly with no crash trace at all, for reasons I did not fully root-cause (likely an interaction between `testing`'s subtest goroutines and Go's signal-fault handler under `go test`'s own process supervision). Only running a genuinely standalone binary (`go run`/a built binary) surfaced the real SIGSEGV. This is exactly the class of trap a project maintaining hand-rolled memory-safety code would need airtight test scaffolding to avoid shipping past — a real cost of the "small and auditable" argument for hand-rolling.

### Go GC copying semantics for heap `[]byte` vs off-heap — verified, precise mechanism
- Go's GC is **non-moving/non-compacting** for heap objects in the current implementation — it does not relocate live heap allocations during collection the way e.g. a JVM generational-copying collector can. That is *not* the primary mechanism behind "a `[]byte` cannot be reliably zeroized."
- The real mechanism: **ordinary Go code (including stdlib) routinely creates independent copies of a `[]byte`'s contents** — `string(b)` conversion (unconditional copy; strings are immutable), `append` past capacity (reallocates and copies; the old backing array becomes unreachable garbage that a zeroing loop has no reference to), embedding in another struct, capturing in an interface, etc. Each copy is a separate heap allocation at a separate address; "zero the original slice" only ever reaches the one address a live reference still points to.
- **Reproduced directly, not asserted**: wrote a unique 32-byte marker, ran realistic operations on it (`string()` conversion, an `append`-driven backing-array growth, `fmt.Sprintf`), forced 5 `runtime.GC()` cycles, zeroed the one slice still referenced, then scanned this process's own writable memory (`/proc/self/maps` + `/proc/self/mem` — reading your own process's memory needs no special privilege regardless of `PR_SET_DUMPABLE`/Yama, those only gate *other* processes reading you) for the marker. Result: **3 surviving copies**, reproduced identically across 3 separate runs (zero variance).
- **Specific, concrete finding for `custody.go` itself**: `Key.aead cipher.AEAD` wraps `crypto/aes.NewCipher`, whose underlying `crypto/internal/fips140/aes.blockExpanded` struct holds the AES round-key schedule as `enc [60]uint32; dec [60]uint32` — inline fields, copied out of *any* raw key buffer (heap, memguard, or hand-rolled) the moment `custody.NewKey` runs, on the ordinary Go heap, with **no exposed `Zero()`/`Destroy()` in the stdlib API**. Verified end-to-end: put raw key bytes in a `memguard.LockedBuffer`, called `aes.NewCipher`+`cipher.NewGCM` on `lb.Bytes()`, destroyed the `LockedBuffer`, and the derived `cipher.AEAD` **still worked perfectly** — proof the round-key schedule is an independent copy that outlives (and is unprotected by) whatever mechanism guards the raw bytes. This means wrapping `custody.NewKey`'s raw input in memguard/mmap narrows the exposure window (raw bytes before the call, and after `Destroy`) but does **not** close it — a second, smaller, harder-to-reach residual (the derived AEAD state) persists on the ordinary heap for the `*Key`'s full lifetime regardless of which custody mechanism is chosen for the raw bytes.

### PR_SET_DUMPABLE / core dumps / `/proc/<pid>/mem` — verified end-to-end
Built a standalone target binary holding a marked 32-byte buffer, toggled dumpable via `prctl`, used `gdb`/`dd` (same user, no `CAP_SYS_PTRACE`) as the "attacker":
- `dumpable=1` (default): `gdb -p <pid>` attaches successfully; `dd if=/proc/<pid>/mem` reads successfully.
- `dumpable=0`: `gdb -p <pid>` fails with `ptrace: Operation not permitted`; `dd if=/proc/<pid>/mem` fails with `Permission denied` (the `open()` itself is refused).
- **Go-specific core-dump gotcha, verified**: Go's default fatal-signal handler intercepts `SIGABRT`/`SIGSEGV` and prints its own traceback instead of letting the OS coredump — `ulimit -c unlimited` alone is not sufficient for a Go binary; `GOTRACEBACK=crash` is also required, or no core file is ever produced regardless of the dumpable flag (a false sense of "protection" if untested). With both set: `dumpable=1` produced a real 42MB `core.<pid>` file (shell reported `(core dumped)`); `dumpable=0` produced **no core file at all** (plain `Aborted`, confirmed via directory listing).
- Neither memguard nor the hand-rolled prototype sets `PR_SET_DUMPABLE` — it is a one-time, process-wide, cheap call brokerd must make itself at boot.

### What was NOT resolved (explicit)
- Whether 8MB `RLIMIT_MEMLOCK` is a true host ceiling or an artifact of this sandboxed session's stripped capabilities (see above) — needs re-verification under a real systemd unit before being treated as fixed.
- SaaS multi-tenant custody (capability-broker.md open question 3) — out of scope; this spike only evaluated the single-tenant, single-process shape the current decision log describes.
- Which exact typed-failure-taxonomy code (`docs/capability-broker.md`'s `NO_GRANT`/`SCOPE_DENIED`/`LOCKED`/`CONTENDED`/`BACKEND_UNREACHABLE`/`RATE_LIMITED`) a recovered mlock-exhaustion panic should surface — neither existing code is a clean semantic fit; flagging for design time, not resolving here.

### Recommendation

Use **memguard** (`github.com/awnumar/memguard`, currently v0.23.0) as the mechanism for holding decrypted signing-key material in `brokerd`, not a hand-rolled mmap+mlock implementation. The hand-rolled version works and is small, but buys no measurable advantage on this host — mlock economics are identical (one page per key either way, since the OS enforces page-granularity locking regardless of implementation) — while giving up memguard's `Enclave` (AES-encrypts buffers when not actively open, shrinking the live-plaintext window during a grant's duration) and canary-based corruption detection, both real properties that would otherwise need to be re-derived and then maintained by chuvar itself, in exactly the class of memory-safety code where a subtle mistake is a silent security hole rather than a build failure. Given chuvar's team size and AGENTS.md's review-discipline bar, a widely-used, previously-reviewed library is the better bet than a project-maintained one-off, and it costs only `golang.org/x/sys` as a new transitive dependency, already present indirectly.

However, memguard must not be dropped in as-is — this spike surfaced three behaviors that are brokerd's responsibility to handle, none of which the library does for you: (1) **wrap every custody-allocation call site in `recover()`** and treat a recovered panic as an operational allocation failure mapped to a typed-taxonomy response (verified the panic is a normal, recoverable Go panic — not a fatal runtime error — but also verified that hitting the RLIMIT_MEMLOCK ceiling wipes *every* currently-held key as a side effect of `Purge()`, not just the failing allocation, so this must be handled as a deliberate, audited tripwire event, consistent with AGENTS.md's fail-closed tripwire principle, rather than an ungraceful crash a process supervisor silently restarts past); (2) **enforce brokerd's own concurrent-grant ceiling** well below the mlock-derived budget (measured 512 32-byte keys on this host's 8MB default `RLIMIT_MEMLOCK`; the real formula is `floor(RLIMIT_MEMLOCK / pagesize)`, so document it in those terms rather than a bare number, and re-verify the 8MB figure isn't a sandbox artifact before treating it as fixed) — for chuvar's actual personal/small-org scale this ceiling is already generous, so the ceiling itself doubles as the anomaly tripwire capability-broker.md's open question 5 already proposed; (3) **only use `NewBuffer(n)+Copy(raw)`** (mutable) for anything brokerd intends to `Wipe()` mid-lifetime — never `Wipe()` a buffer obtained via `NewBufferFromBytes`, which is silently `Freeze()`d and SIGSEGVs on write; (4) **call `PR_SET_DUMPABLE=0` explicitly at process boot** (memguard does not do this — confirmed by source inspection and live measurement) and don't rely on memguard's per-buffer `MADV_DONTDUMP` for anything beyond core-dump exclusion of the guarded pages themselves.

Name the residual explicitly rather than letting the eventual `custody.go` doc-comment update overclaim: even with memguard wrapping the raw key bytes, the derived AES round-key schedule that `custody.NewKey`/`crypto/aes.NewCipher` produces lives in ordinary, un-mlocked, un-guarded Go heap memory for the `*Key`'s full lifetime, with no stdlib zeroization hook — confirmed by destroying a memguard-backed raw key and showing the derived `cipher.AEAD` keeps working. Re-deriving the AEAD just-in-time per signing operation would close this but reintroduces the custody backend into the hot signing path, which the 2026-08-09 "shared consent plane, separate execution plane" decision specifically avoided — so the practical mitigation for this narrower surface is exactly (4), process-wide `PR_SET_DUMPABLE=0`, not per-buffer guarding, and it should be stated in the code/docs as "narrowed, not closed," matching the project's existing standard of not writing a security claim the mechanism doesn't back.
